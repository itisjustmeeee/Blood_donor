# Guide для новых разработчиков

## 1. Назначение проекта

Проект — консольное приложение центра донорства крови.

Оно поддерживает:

- регистрацию и вход доноров и врачей;
- запись на медицинское обследование;
- обработку результатов обследований;
- запись на донацию;
- обработку донаций врачом;
- учёт партий крови;
- просмотр и фильтрацию обследований и донаций;
- статистику и экспорт в CSV/Excel;
- автоматическое создание базы PostgreSQL и тестовых данных.

Основная архитектура:

```
Console UI -> Service -> Repository / JDBC -> PostgreSQL
```

В проекте используется PostgreSQL.<br>
В документации иногда встречается формулировка `MySQL / PostgreSQL` как обозначение реляционной СУБД, но фактические SQL-запросы и JDBC-подключение настроены на PostgreSQL.

## 2. Структура каталогов

```
src/main/java/ru/mirea/project/
├── Main.java

├── ui/
├── exception/
├── security/

sql_script/

```

### `Main.java`

Точка входа приложения. Настраивает UTF-8 для стандартного вывода и вызывает `DatabaseInitializer.initialize()`.<br>
После успешной инициализации запускается `new ConsoleUI().start()`.

### `ui/ConsoleUI.java`

Единственный класс пользовательского интерфейса.

Функции:

- выводит главное меню;
- считывает команды и данные пользователя;
- вызывает сервисы;
- отображает результаты и сообщения об ошибках;
- запускает фильтрацию, сортировку, статистику и экспорт.

UI только собирает данные и передает их в Service.

### `model/`

Предметные модели проекта.<br>
Все модели представлены Java `record`, поэтому содержат неизменяемые поля, конструктор и методы доступа автоматически.

### `repository/`

Слой хранения данных.<br>
Репозитории выполняют SQL через JDBC и преобразуют строки `ResultSet` в объекты моделей.

### `service/`

Слой бизнес-логики.<br>
Здесь проверяются возраст, вес, статусы, связь обследования с донацией, доступность партии крови и другие правила предметной области.

### `exception/`

Собственные исключения бизнес-слоя:

- `BusinessException` — базовое бизнес-исключение;
- `RegistrationException` — ошибка регистрации или изменения профиля;
- `DonationEligibilityException` — донор не допущен к обследованию или донации;
- `ExaminationValidationException` — ошибка обработки медицинского обследования;
- `BloodBatchException` — ошибка партии крови;
- `EntityNotFoundException` — объект не найден.

### `util/`

- `DatabaseManager` — создание JDBC-соединений;
- `DatabaseInitializer` — создание базы, таблиц и миграций;
- `ExcelExporter` — экспорт CSV и XLSX;
- `TestDataSeeder` — добавление демонстрационных пользователей и записей.

### `security/PasswordHasher.java`

Хеширует пароли с помощью SHA-256 и проверяет введённый пароль по сохранённому хешу.

## 3. Модели

### `Donor`

Описывает пользователя системы.

Содержит поля:

- `id`;
- `fullName`;
- `age`;
- `role` — `donor` или `doctor`;
- `gender` — `male` или `female` в базе;
- `weight`;
- `email`;
- хеш пароля;
- идентификатор и отображение группы крови.

### `BloodGroup`

Группа крови и резус-фактор

Содержит поля:

- `bloodType`: `0`, `A`, `B`, `AB`;
- `rhFactor`: `+`, `-`.

### `DonationRequest`

Заявка с датой и статусом.<br>
Используется для записи на обследование и записи на донацию.<br>
Связана с донором через `donor_id`.

### `MedicalExamination`

Запись на медицинское обследование.

Содержит поля:

- идентификатор обследования;
- `requestId`;
- дата;
- гемоглобин;
- давление;
- заключение;
- статус допуска;
- ФИО донора для удобного вывода врачу.

### `Donation`

Фактическая донация

Содержит поля:

- обследование, на основании которого выполнена донация;
- партия крови;
- дата;
- объём;
- тип донации;
- результат;
- ФИО донора;
- группа крови партии.

В базе на `examination_id` установлен `UNIQUE`, поэтому одно обследование нельзя использовать более чем в одной донации.

### `BloodBatch`

Партия крови.

Содержит поля:

- номер партии;
- группа крови;
- даты заготовки и окончания годности;
- общий объём;
- статус.

## 4. Главное меню и меню ролей

Главное меню находится в методе `ConsoleUI.start()`

Вывод главного меню:

```
1. Регистрация
2. Вход
3. Проверить подключение
4. Внести тестовые данные
0. Выход
```

После входа роль определяется по `Donor.role()`:

- `donor` получает меню донора;
- `doctor` получает меню врача.

Меню донора реализовано в `donorMenu()`, меню врача — в `doctorMenu()`.

## 5. Слой Service и бизнес-логика

### `DonorService`

Реализует:

- регистрацию;
- проверку email;
- проверку роли и пола;
- проверку возраста не менее 18 лет;
- проверку веса не менее 50 кг;
- проверку выбранной группы крови;
- аутентификацию;
- изменение возраста, веса и пола в профиле.

### `DonationService`

Реализует:

- запись на медицинское обследование;
- проверку возраста и веса;
- проверку гемоглобина;
- запрет новой нерассмотренной заявки;
- запись на донацию только после положительного обследования;
- правило «одно обследование — одна донация»;
- проверку даты донации относительно обследования;
- проверку объёма;
- проверку соответствия группы крови партии и донора;
- завершение заявки после оформления донации.

### `MedicalExaminationService`

Реализует:

- обработку обследования врачом;
- проверку нормы гемоглобина;
- изменение даты обследования;
- удаление обследования;
- изменение врачом даты, гемоглобина, давления, заключения и статуса.

Донор может менять дату только активной записи без вынесенного заключения.<br>
Врач может редактировать завершённые обследования.

### Репозитории

Репозитории выполняют операции с БД:

- `DonorRepository` — доноры и профили;
- `BloodGroupRepository` — группы крови;
- `DonationRequestRepository` — заявки;
- `MedicalExaminationRepository` — обследования;
- `DonationRepository` — донации;
- `BloodBatchRepository` — партии.

## 6. CRUD для записи на медицинское обследование

Основная CRUD-сущность в проекте — запись на медицинское обследование.

### Create

Запуск из `ConsoleUI.bookExamination()`;
бизнес-проверки — в `DonationService.bookExamination()`;
SQL-вставки — в:

- `DonationRequestRepository.create()`;
- `MedicalExaminationRepository.create()`.

Создаётся заявка `donation_request` и связанное обследование `medical_examination`.

### Read

Используются:

- `findByDonor()` — обследования текущего донора;
- `findAll()` — все обследования для врача;
- `findById()` — обследование по идентификатору;
- `findByIdAndDonor()` — проверка принадлежности обследования донору.

### Update

Дата меняется через `MedicalExaminationRepository.updateDate()`.<br>
В одной транзакции синхронно обновляются дата обследования и дата связанной заявки.

Изменение медицинского результата Врачом выполняется через `updateResult()`, который изменяет гемоглобин, давление, заключение и статус.

### Delete

Удаление выполняется через `deleteWithRequest()`:

1. находится связанная заявка;
2. проверяется отсутствие донации;
3. удаляется обследование;
4. удаляется заявка;
5. выполняется `commit`.

Обследование, по которому уже оформлена донация, удалить нельзя.

## 7. Enum

В Java-коде статусы передаются строками, а настоящие enum-типы определены в PostgreSQL в `sql_script/blood_donor.sql`, который при первом запуске читает `DatabaseInitializer`:

- `user_role`;
- `gender`;
- `admission_status`;
- `request_status`;
- `donation_type`;
- `batch_status`;
- `donation_result`.

Примеры значений:

```
user_role: donor, doctor
admission_status: pending, accepted, rejected
request_status: created, confirmed, completed, cancelled
batch_status: available, reserved, used, expired, disposed
```

При записи значения передаются с явным приведением, например `?::request_status` или `?::donation_result`.<br>
Это защищает базу от недопустимых статусов.

## 8. Инкапсуляция, интерфейсы и полиморфизм

### Инкапсуляция

Состояние скрыто внутри классов:

- поля сервисов и репозиториев объявлены `private final`;
- подключение и параметры базы скрыты в `DatabaseManager`;
- хеширование скрыто в `PasswordHasher`;
- SQL не находится в UI;
- UI не работает с JDBC напрямую для обычных операций.

Модели `record` предоставляют безопасный доступ к данным через методы компонентов и не позволяют произвольно менять их состояние.

### Интерфейс

Интерфейс `BloodBatchSorter` задаёт общий контракт:

```
List<BloodBatch> sort(List<BloodBatch> batches);
```

Реализации:

- `AscendingBloodBatchSorter`;
- `DescendingBloodBatchSorter`.

### Полиморфизм

В `ConsoleUI.bloodBatchMenu()` переменная имеет тип `BloodBatchSorter`, но фактически содержит одну из реализаций.<br>
Вызов `sort()` выполняется полиморфно — конкретный алгоритм выбирается во время выполнения.

## 9. Коллекции, поиск, фильтрация и сортировка

В проекте используются `List`, `ArrayList`, `Stream API`, `filter`, `map`, `sorted`, `toList`, `max`, `sum`, `count`.

### Поиск и фильтрация обследований

В `ConsoleUI.donorExaminations()` доступны:

- все обследования;
- фильтр по статусу;
- фильтр по месяцу и году.

### Поиск донаций

В `donorDonations()` и `doctorDonations()` доступны:

- вывод всех донаций;
- поиск за выбранный месяц и год.

### Сортировка партий

В `bloodBatchMenu()` пользователь выбирает:

- по `totalVolume` по возрастанию;
- по `totalVolume` по убыванию;
- без сортировки.

Сортировка реализована через `BloodBatchSorter` и Stream API.

## 10. Статистика и экспорт

Статистика формируется в `ConsoleUI`:

- `donorStatistics()` — статистика конкретного донора;
- `doctorStatistics()` — статистика всего центра.

Собираются:

- количество заявок;
- количество обследований;
- число допущенных и отклонённых;
- количество донаций;
- общий объём крови;
- подробные строки обследований, заявок и донаций.

Метод `printStatistics()` выводит данные в консоль.<br>
Метод `exportStatistics()` предлагает:

```
1 — CSV
2 — Excel (.xlsx)
0 — не экспортировать
```

`ExcelExporter` открывает системный `JFileChooser`, позволяет выбрать имя и папку, также предупреждает о перезаписи и сохраняет файл:

- CSV — UTF-8 с BOM и разделителем `;`;
- XLSX — через Apache POI, с автоматической шириной столбцов.

## 11. Тестовые данные

Пункт **«Внести тестовые данные»** находится в главном меню `ConsoleUI.start()`.<br>
Он вызывает `TestDataSeeder.seed()`.

Добавляются:

- донор с несколькими обследованиями и донациями;
- донор с обследованием без донации;
- донор с положительным обследованием и донацией;
- донор с отклонённым обследованием;
- врач;

Загрузка идемпотентна: маркерный email проверяется перед вставкой, поэтому повторный запуск не создаёт дубликаты.<br>

## 12. JDBC

### Подключение

`DatabaseManager` использует:

```
DriverManager.getConnection(URL, USER, PASSWORD)
```

`DatabaseInitializer` дополнительно подключается к системной базе `postgres`, проверяет наличие `blood_donor` и создаёт её при отсутствии.

### `Connection`

`Connection` представляет соединение с PostgreSQL.<br>
В проекте соединения создаются на время конкретной операции и закрываются автоматически.

### `PreparedStatement`

Основной способ выполнения пользовательских SQL-запросов.

Пример:

```
try (var statement = connection.prepareStatement(
        "SELECT ... FROM donor WHERE donor_id=?")) {
    statement.setInt(1, donorId);
    try (var rows = statement.executeQuery()) {
        ...
    }
}
```

Плюсы:

- параметры отделены от SQL;
- защита от SQL-инъекций;
- типы значений задаются через `setInt`, `setString`, `setDate`, `setBigDecimal`;
- запрос проще читать и переиспользовать.

### `ResultSet`

`ResultSet` содержит строки результата `SELECT`.<br>
В репозиториях он читается через `rows.next()`, после чего вызываются `getInt`, `getString`, `getDate`, `getBigDecimal` и `getBoolean`.

### try-with-resources

Все JDBC-ресурсы закрываются через try-with-resources:

- `Connection`;
- `PreparedStatement`;
- `Statement`;
- `ResultSet`.

Это предотвращает утечки соединений и незакрытые курсоры.

### `Statement` и `PreparedStatement`

`Statement` используется для статических служебных операций.

Например:

- `CREATE TABLE`;
- `ALTER TABLE`;
- `CREATE DATABASE`;
- миграций схемы.

`PreparedStatement` используется для операций с данными и параметрами:

- регистрация;
- поиск по идентификатору;
- изменение профиля;
- создание заявок;
- создание донаций;
- фильтры по донору.

В проекте динамические значения передаются параметрами через `?`.

## 13. Связи между таблицами

Основные таблицы и связи:

```
blood_group 1 ─── N donor
donor 1 ─── N donation_request
donation_request 1 ─── 0..1 medical_examination
medical_examination 1 ─── 0..1 donation
blood_batch 1 ─── N donation
```

Подробно:

- `donor.blood_group_id` -> `blood_group.blood_group_id`;
- `donation_request.donor_id` -> `donor.donor_id`;
- `medical_examination.request_id` -> `donation_request.request_id`;
- `donation.examination_id` -> `medical_examination.examination_id`;
- `donation.batch_id` -> `blood_batch.batch_id`.

`medical_examination.request_id` уникален, поэтому заявка имеет максимум одно обследование.<br>
`donation.examination_id` уникален, поэтому обследование имеет максимум одну донацию.

## 14. Исключения

Ошибки разделяются на:

- `SQLException` — техническая ошибка PostgreSQL/JDBC;
- `BusinessException` и наследники — нарушение бизнес-правил;
- `EntityNotFoundException` — отсутствие требуемой записи.

Service выбрасывает понятные бизнес-исключения, а `ConsoleUI` перехватывает их и выводит сообщение пользователю.<br>
SQL-ошибки передаются в `databaseError(...)` или обрабатываются локально, если пользователь должен остаться в текущем меню.

## 15. Основные бизнес-правила

1. Регистрация пользователя младше 18 лет запрещена;
2. Вес донора должен быть не менее 50 кг;
3. Донору обязательна группа крови и резус-фактор;
4. Пол допускается только `male` или `female` (в UI отображается как `муж.` и `жен.`);
5. При записи на обследование проверяется возраст, вес и гемоглобин;
6. Норма гемоглобина для мужчин — 130–160 г/л, для женщин — 120–140 г/л;
7. Нельзя создать новую нерассмотренную заявку при наличии предыдущей;
8. На донацию допускается только положительное обследование;
9. Одно положительное обследование может использоваться только для одной донации;
10. Объём одной донации — от 1 до 450 мл;
11. Группа крови донора должна совпадать с группой выбранной партии;
12. Заполненная партия переводится в `reserved`;
13. Срок годности партии должен быть позже даты заготовки;
14. Донор может менять дату только активного обследования;
15. Врач может изменять результаты обследования и работать с завершёнными обследованиями;
16. Обследование, использованное в донации, удалять нельзя.

## 16. Создание, изменение и удаление данных

Типовой путь операции:

```
ConsoleUI
  -> Service
    -> Repository
      -> PreparedStatement
        -> PostgreSQL
```

Примеры:

- создание обследования:

1. UI собирает дату и гемоглобин.
2. `DonationService` проверяет правила.
3. `DonationRequestRepository` создаёт заявку.
4. `MedicalExaminationRepository` создаёт обследование.
5. UI выводит идентификатор созданной записи.

При изменении сервис проверяет права роли, принадлежность записи и её статус.<br>
При удалении обследования репозиторий использует транзакцию, чтобы не оставить заявку без обследования или обследование без заявки.

## 17. Инициализация базы

При запуске:

1. `DatabaseInitializer` проверяет наличие БД `blood_donor`.
2. При отсутствии база создаётся через системную БД `postgres`.
3. Создаются PostgreSQL enum-типы и таблицы.
4. Выполняется миграция старых полей возраста и телефона.
5. `ConsoleUI.start()` добавляет стандартные группы крови и партии.

Партии создаются для всех восьми комбинаций типов крови:

```
0+, 0-, A+, A-, B+, B-, AB+, AB-
```

## 18. Настройка подключения к PostgreSQL

Параметры подключения находятся в `util/DatabaseManager`, но пароль не хранится в исходном коде.<br>
Приложение читает переменные окружения:

- `BLOOD_DB_HOST`;
- `BLOOD_DB_PORT`;
- `BLOOD_DB_NAME`;
- `BLOOD_DB_USER`;
- `BLOOD_DB_PASSWORD`.

Например:

```
$env:BLOOD_DB_USER = "postgres"
$env:BLOOD_DB_PASSWORD = "пароль PostgreSQL"
```

## 19. Как запускать и проверять проект

Из каталога `bloodcenter` прописать команды:

```
mvn clean test
mvn exec:java
```

Требуется PostgreSQL и пользователь, имеющий право на создание базы `blood_donor`.<br>
При создании новой базы схема читается из `sql_script/blood_donor.sql`.

Актуальная ER-диаграмма находится в [`er-diagram.md`](er-diagram.md).
